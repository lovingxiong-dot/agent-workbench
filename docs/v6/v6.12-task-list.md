# v6.12 Task List — PresentationModel + Task 闭环

> **主线目标**：让 Workbench 从「有架构的框架」变成「可用的产品」。
>
> v6.11 完成了 Metadata Contract 与 Provider Registry；v6.12 的重点是：
> 1. 用 PresentationModel 彻底隔离 UI 与 Runtime。
> 2. 跑通第一条真实任务闭环（User → Manager → Planning → Capability → Provider → Streaming → Task → Trace → History）。
> 3. 通过真实使用验证架构稳定性，而不是继续增加抽象层。

---

## 全局约束

- **Metadata Contract 已冻结**（见 `PROJECT_BLUEPRINT.md`）：只允许 Additive Change，禁止 Breaking Change。
- **不再新增 Provider**：当前 7 个内置 Provider 已足够验证 Registry；未来 Provider 必须做到「零代码改动」接入。
- **UI 不拥有 Runtime / Provider / Resource**：UI 只通过 `PresentationModel` 读取，通过事件反向通信。

---

### 附属小功能：Conversation 自动标题（v6.12.0-alpha.2）

> 用户感知强，但实现必须放在 Conversation Domain，而不是 UI 层。

#### 目标
模拟 ChatGPT 体验：新会话默认显示 `New Conversation`，第一轮 Assistant 回复完成后，异步生成标题并更新左侧 Navigator，全程不阻塞 Streaming。

#### 文件规划
- `agent_workbench/conversation/title_generator.py` — 标题生成策略接口与规则实现。
- `agent_workbench/conversation/title_service.py` — `ConversationTitleService`，协调生成与保存。
- `agent_workbench/conversation/manager.py`（或现有会话管理层）— 在 Assistant 第一轮回复完成后触发标题生成。
- `agent_workbench/conversation/store.py`（或现有 Store）— 保存 `Conversation.title` 与 `title_source`。

#### 任务
- [ ] 创建 `TitleGenerator` 协议 / 抽象类：
  - `RuleTitleGenerator`：取用户第一句话前 N 字或按关键词截断。
  - 预留 `LLMTitleGenerator`：调用模型总结（后续接入）。
  - 预留 `HybridTitleGenerator`：规则失败再调用 LLM。
- [ ] 创建 `ConversationTitleService.generate_title(conversation)`，异步执行，不阻塞主线程。
- [ ] 会话创建时默认 `title=""`，Navigator 渲染为 `New Conversation`。
- [ ] Assistant 第一轮回复完成后，若 `title == ""` 且未被用户手动修改（`title_source != "user"`），触发标题生成。
- [ ] 生成后更新 `Conversation.title` → `ConversationStore.update()` → `EventBus` → Navigator 自动刷新。
- [ ] 用户手动重命名后设置 `title_source="user"`/`title_locked=True`，自动标题不再覆盖。

#### 验收标准
- [ ] 新建会话左侧显示 `New Conversation`。
- [ ] 第一轮 Assistant 回复完成后，左侧标题自动变为生成的短标题（如 `Python 文件分析`）。
- [ ] 标题生成过程不影响 Streaming 输出。
- [ ] 用户手动修改标题后，自动标题不再覆盖。

## Commit 9：Task 闭环（v6.12.0-beta.2）

### 目标
跑通第一条真实任务，例如：

```text
User: 帮我分析这个 Python 文件。
```

全过程：

```text
User → Manager → Planning → Capability → Provider → Streaming → Task → Trace → History
```

### 文件规划
- `agent_workbench/runtime/manager/` 或 `agent_workbench/services/manager.py`
- `agent_workbench/runtime/task_executor.py`（如需要）
- `agent_workbench/ui/workbench/chat_workspace.py`
- `agent_workbench/ui/workbench/trace_workspace.py`
- `tests/runtime/test_task_end_to_end.py`

### 任务
- [ ] Manager 接收到用户请求后，能生成一个 `Task`（不是简单 chat）。
- [ ] Task 经过 Planning 层，选择合适的 Capability + Provider + Resource。
- [ ] Task 执行过程中产生 Trace（请求、响应、token、耗时）。
- [ ] Task 结果通过 Streaming 返回 UI，并在 Chat Workspace 显示。
- [ ] Task 完成后保存到 Session History，可回放。
- [ ] 提供一条端到端测试，用 `EchoProvider` 验证完整链路。

### 验收标准
- [ ] 用户输入一个任务指令后，能看到 AI 流式回复，且 Trace 中记录了完整执行步骤。
- [ ] 刷新 Session 后，历史记录仍存在。
- [ ] `pytest` 全量通过。

## 现在不做清单（v6.12 期间）

- **新增 Provider**：Registry 已足够，后续 Provider 必须零代码接入。
- **新增 Runtime 类型**：Knowledge / Persona / Browser / Plugin / Gateway / Digital Identity 不接。
- **Schema-driven UI**：v6.12 仍手动映射 PresentationModel，v6.13.x 再考虑从 Schema 自动生成控件。
- **Runtime Executors**：ProviderRuntime / ToolRuntime / SkillRuntime 放到 Schema Foundation 之后。
- **复杂 Workflow DAG**：只做基础串行任务流 A → B → C，且放到更晚阶段。
- **Multi-Agent / Marketplace / Remote / Web Plugin**：在 Task 闭环稳定前不做。
