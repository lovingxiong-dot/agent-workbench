## Context

v6.9.2-alpha 已完成 **Single Agent Runtime Foundation**：

* `Task` 固定为 `id / capability / payload / metadata / created_at` 五字段。

* `UserRequest → Manager → Task → submit_task()` 主链固定。

* `WorkbenchHost → Workbench → 五大 Host` UI 骨架固定。

* 全量测试 210/210 通过（`pytest tests/v6/` 184/184，`$env:PYTHONPATH="."; pytest agent_workbench/tests/` 26/26）。

下一阶段目标不是 Multi-Agent，而是把 **Capability 提升为 Runtime 一级公民**：让单实例 Agent 拥有可发现、可路由、可组合的能力树，形成 `Manager → Capability Registry → Capability Router → Task → Capability Chain → Engine` 的 Runtime 主链。UI 在前半段不接入，后半段通过 EventBus + Runtime UI Bridge 接入。

## Goals

1. 形式化 Capability：从 metadata 升级为运行时对象 `CapabilityDefinition`，含 id/name/description/providers/input\_schema/output\_schema/permissions/cost/latency/parent\_id/keywords/engine\_capability/persona。
2. 建立 Capability Tree：支持层次化能力关系（如 assistant → coding → python → debugging）。v6.9.3 只实现树（parent\_id + children + lineage），不引入 DAG、图搜索、权重传播、自动规划。
3. 引入 Manager 路由层：`ManagerRuntime` 将 `UserRequest` 解析为 `CapabilityMatch`，再生成 `Task`。
4. 支持 Capability Chain：`Task.metadata["capability_chain"]` 携带多步能力执行序列，Orchestrator 顺序执行。Chain 只控制 Capability 顺序，不控制 Engine / Provider / Policy / Retry。
5. 引入 Capability Persona：作为 metadata 策略，为未来 Agent Identity 奠基。
6. 保持 Task 五字段不变；所有扩展进 metadata/payload。
7. 不实现：Multi-Agent 对话、Agent Memory、MCP 大规模接入。
8. 测试目标：全量 260\~280 passed。

## Non-Goals

* 不新增 RuntimeModule（V6 Feature Freeze：仅现有 10 模块）。

* 不修改 Task 核心字段。

* 不做 LLM-based Manager（v6.9.3 使用规则策略，保留替换接口）。

* 不做自治循环 / ReAct / Agent 协作。

* 不做复杂图算法（DAG、权重传播、自动规划）。

## Development Constraints

1. **CapabilityDefinition 纯数据，不携带 Runtime 状态**：允许 `id/name/parent_id/engine_capability/providers/...` 等静态描述；禁止 `current_task/running_provider/last_result` 等运行时状态。Capability 不是 Service。
2. **CapabilityRegistry 生命周期单例**：由 `AgentWorkbenchRuntime` 创建并持有，注入 `ManagerRuntime` 与 `CapabilityRouter`。禁止 Manager 或 Router 自行实例化 Registry。
3. **Capability Chain 第一版仅静态链**：链在 Manager 阶段一次性生成，Orchestrator 按顺序执行。禁止根据中间结果动态追加步骤。
4. **ManagerRuntime 不调用 Engine**：Manager 只负责 `UserRequest → Task`，执行完全交给 Runtime/Orchestrator。
5. **UI Bridge 第一版只读**：仅 `Runtime → UI` 事件流，不允许 UI 通过 Bridge 反向下发 Runtime 命令。
6. **能力树根节点使用** **`assistant`**：避免与 Manager 调度器语义混淆。

## Architecture

```
UserRequest
    │
    ▼
WorkbenchController.chat() / chat_with_tool()
    │
    ▼
ManagerRuntime.resolve(request)
    ├─ classify(request) → CapabilityIntent
    ├─ CapabilityRegistry.resolve(intent) → CapabilityMatch
    ├─ 可选：生成 CapabilityStep 链
    └─ 构建 Task
         ├─ capability = definition.engine_capability
         ├─ metadata["capability_id"] = node.id
         ├─ metadata["capability_path"] = [assistant, coding, python, debugging]
         ├─ metadata["capability_name"] = match.definition.name
         ├─ metadata["capability_persona"] = {...}
         └─ metadata["capability_chain"] = [CapabilityStep, ...]  (可选)
    │
    ▼
AgentWorkbenchRuntime.submit_task(task)
    │
    ▼
CoreAgentRuntime.orchestrate(task) → Orchestrator.submit(task)
    │
    ▼
Orchestrator._execute_task(ctx)
    ├─ CapabilityRouter.resolve(ctx) → engine capability
    │     └─ 发布 CAPABILITY_RESOLVED
    ├─ 若存在 capability_chain：循环执行 CapabilityStep
    │     每步：设置 task_type → PlannerLoop/RuleBasedDecisionPolicy → EngineManager
    └─ 单步：原有 PlannerLoop → EngineManager 路径
    │
    ▼
EngineManager.select_engine({"capability": engine_capability})
    │
    ▼
WorkbenchLLMEngine / WorkbenchToolEngine 执行并发布事件
    │
    ▼
EventBus → WorkbenchRuntimeBridge → Workbench Host UI
```

### 目标

### 新增/完善文件

### 修改文件

#### `v6/runtime/orchestrator.py`

* `_execute_task` 中增加能力链分支：

  * 若 `ctx.metadata["capability_chain"]` 存在，调用 `_execute_chain(task_id, ctx, chain)`。

  * 链式执行每步前设置 `ctx.metadata["task_type"] = step.engine_capability`。

  * 每步执行前发布 `CAPABILITY_CHAIN_STEP_STARTED` 事件。

* 单步执行路径保持原样。

```python
def _execute_chain(self, task_id: str, ctx: RuntimeContext, chain: list[CapabilityStep]) -> None:
    for index, step in enumerate(chain):
        self._publish(
            RuntimeEventType.CAPABILITY_CHAIN_STEP_STARTED,
            {
                "step_index": index,
                "capability_id": step.capability_id,
                "engine_capability": step.engine_capability,
            },
            task_id=task_id,
            source="orchestrator",
        )
        ctx.metadata["task_type"] = step.engine_capability
        ctx.metadata["capability_id"] = step.capability_id
        decision = self._make_decision(ctx, step.engine_capability)
        # 执行决策；若失败则终止链
        ...
    self._complete_task(task_id, {"reason": "capability chain finished"})
```

## Risk & Mitigation

| 风险                                        | 缓解                                                                                      |
| ----------------------------------------- | --------------------------------------------------------------------------------------- |
| 与既有 `v6.runtime.capability_registry` 命名混淆 | 新 registry 位于 `agent_workbench.runtime.capability`，类名在应用 Runtime 层；旧的 Engine 能力注册表完全不动。 |
| Controller 默认 Manager 改动导致旧测试失败           | 保持 `AgentManager` 类不变；仅修改默认注入。`test_manager.py` 直接构造 `AgentManager`，不受影响。               |
| Orchestrator 链式执行破坏单步任务                   | 链式逻辑用独立 `_execute_chain` 分支；无 `capability_chain` 时严格走原 `_execute_task` 逻辑。              |
| Task 模型膨胀                                 | 核心五字段不变；能力链、Persona 全部写入 metadata。                                                      |
| Capability Graph 过度设计                     | v6.9.3 只实现 Tree（parent/children/lineage），不引入 DAG/图搜索/自动规划。                              |
| Chain 变成第二套 Planner                       | Chain 只控制 Capability 顺序，不控制 Engine/Provider/Policy/Retry。                               |
| UI 过早绑定 Runtime 细节                        | UI Bridge 只持有 EventBus 与 Host 引用；不持有 Runtime 业务对象。                                      |
